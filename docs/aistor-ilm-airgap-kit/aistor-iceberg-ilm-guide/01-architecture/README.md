# 01. 아키텍처

## 1. 전체 구성도

```
┌──────────────────────────── Kubernetes 클러스터 ────────────────────────────┐
│                                                                             │
│   ┌──────────────┐        ┌──────────────┐        ┌────────────────────┐   │
│   │ Spark Driver │◄──────►│  Executors   │        │  Hive Metastore    │   │
│   │  (Pod)       │        │  (Pod × N)   │        │  (Thrift :9083)    │   │
│   └──────┬───────┘        └──────┬───────┘        └─────────┬──────────┘   │
│          │  ①테이블 위치 조회/커밋            │                   │              │
│          └──────────────────┬────────────────┴───────────────┘              │
│                             │                                                │
└─────────────────────────────┼────────────────────────────────────────────────┘
                              │ ② S3 API (GET/PUT/LIST)  — 유일한 데이터 경로
                              ▼
        ┌────────────────────────────────────────────────────┐
        │            HOT 클러스터 (AIStor / MinIO)            │
        │   버킷: warehouse   (Versioning: Enabled)          │
        │   ┌──────────────────────────────────────────┐    │
        │   │  metadata/  ← 전이 제외 (항상 로컬 상주)    │    │
        │   │  data/      ← 1일 후 transition 대상       │    │
        │   └──────────────────────────────────────────┘    │
        │   Scanner ─ ILM 규칙 평가/실행                      │
        └───────┬──────────────────────────────┬─────────────┘
                │ ③ ILM Transition             │ ④ Replication (비동기)
                │   (data 이동, 로컬은 stub)     │   (객체 사본 생성)
                ▼                              ▼
        ┌───────────────────────┐    ┌───────────────────────┐
        │  WARM 클러스터 (tier)  │    │  WARM 클러스터 (복제)  │
        │  버킷: warm-tier      │    │  버킷: warehouse      │
        └───────────────────────┘    └───────────────────────┘
                 ▲                              ▲
                 └──────── 물리적으로 동일 클러스터일 수 있으나, ─────┘
                            버킷/용도는 반드시 분리할 것 (§4)
```

### 흐름 설명

| # | 흐름 | 프로토콜 | 동기/비동기 | 실패 시 영향 |
|---|---|---|---|---|
| ① | Spark ↔ HMS: 테이블 metadata.json 위치 조회, 커밋 시 포인터 교체 | Thrift | 동기 | 테이블 접근 불가 (읽기/쓰기 전부) |
| ② | Spark ↔ hot: 실제 객체 I/O | S3 HTTPS | 동기 | 쿼리 실패 |
| ③ | hot → warm(tier): ILM transition | S3 HTTPS | 비동기 (Scanner 주도) | 전이 지연. 데이터는 hot에 남아 있으므로 조회는 정상 |
| ③' | hot → warm(tier): 전이된 객체 읽기 | S3 HTTPS | **동기** (쿼리 경로에 포함) | ⚠️ 해당 객체 읽기 실패 = 쿼리 실패 |
| ④ | hot → warm(복제): 객체 복제 | S3 HTTPS | 비동기 | RPO 손실. 평상시 조회에는 무영향 |

⚠️ **③' 이 이 아키텍처의 숨은 동기 의존성입니다.** 전이가 시작된 순간부터 warm 클러스터는 "백업 스토리지"가 아니라 **쿼리 경로상의 필수 컴포넌트**가 됩니다. 이 사실이 11장 장애 시나리오의 출발점입니다.

## 2. 두 가지 hot→warm 방식 — 무엇을 쓰고 있는가

사용 중인 구성이 아래 둘 중 무엇인지(또는 둘 다인지)에 따라 **장애 양상과 복구 절차가 완전히 달라집니다.**

### 방식 A: Remote Tier Transition (계층화)

```
hot: warehouse/data/x.parquet  ──transition──►  warm: warm-tier/<uuid>/...
     (로컬에는 stub만 남음)                        (실제 데이터)

읽기: Spark ──GET──► hot ──내부 GET──► warm ──► hot ──► Spark
                     (hot이 대신 가져와서 응답. Spark는 warm을 모름)
```

| 특성 | 값 |
|---|---|
| 객체 네임스페이스 | hot에 그대로 유지 (LIST하면 보임) |
| hot 용량 | 거의 0으로 감소 (stub만) |
| 읽기 경로 | hot 경유 투명 조회 |
| warm 장애 시 | **해당 객체 읽기 실패** |
| 목적 | 비용 절감 (hot 스토리지 절약) |
| 복사본 수 | 1개 (warm에만 실데이터) — **백업이 아님** |

### 방식 B: Replication + Expiration (복제 후 정리)

```
hot: warehouse/data/x.parquet  ──replicate──►  warm: warehouse/data/x.parquet
     (1일 후 expiration으로 삭제)                (독립 사본, 계속 보존)

읽기: 전이 개념 없음. hot에 있으면 읽히고, 만료되면 hot에서는 안 보임
```

| 특성 | 값 |
|---|---|
| 객체 네임스페이스 | hot에서 만료 시 사라짐 (LIST에서 소멸) |
| hot 용량 | 만료 후 해제 |
| 읽기 경로 | hot에만 존재. 만료된 객체는 **읽을 수 없음** |
| warm 장애 시 | hot 조회에는 무영향 (단, 사본 소실 위험) |
| 목적 | DR / 장기 보존 |
| 복사본 수 | 2개 (만료 전) → 1개 (만료 후, warm만) |

### 🔴 방식 B를 Iceberg에 그대로 쓰면 안 되는 이유

방식 B의 expiration은 **Iceberg가 아직 참조 중인 데이터 파일을 삭제**합니다.
Iceberg는 "이 Parquet 파일은 1년 전에 쓰였지만 현재 스냅샷에서 여전히 유효"한 상태가 정상입니다.
객체 나이(age)와 데이터 유효성은 아무 관계가 없습니다.

```
2026-01-01  data/part-0001.parquet 생성   (스냅샷 S1이 참조)
2026-08-27  여전히 스냅샷 S99가 참조 중     ← 삭제되면 테이블 손상
            그러나 객체 나이는 239일 → ILM expiration은 삭제함
```

따라서 이 환경에서 방식 B를 쓰려면 **Iceberg 데이터 프리픽스는 반드시 제외**해야 합니다.
(자세한 규칙 설계는 [04장](../04-ilm-policy-design/))

### 방식 A + B 동시 적용 시 상호작용 매트릭스

| 상황 | 동작 | 주의 |
|---|---|---|
| 객체가 전이 전 → 복제 | 실데이터가 복제됨 | 정상 |
| 객체가 전이 후 → 복제 대상이 됨 | 🔍 버전/구현에 따라 전이 객체의 복제 동작이 다름. hot이 tier에서 읽어와 복제하거나, 복제가 지연/스킵될 수 있음 | **반드시 실측 필요** (08 T-12) |
| 복제된 후 hot에서 전이 | warm 복제본은 그대로, hot은 stub | warm에 사본 2벌(복제본+tier본) 존재 가능 → 용량 2배 |
| 복제 대상 버킷에 ILM 규칙이 있는가 | 버킷 복제는 **ILM 설정을 자동 동기화하지 않음**. warm 쪽 규칙은 별도 관리 | 규칙 드리프트 위험 |
| 전이 객체 삭제 | hot에서 삭제 시 tier의 데이터도 정리 대상이 됨 | 삭제 전파 타이밍 확인 필요 |

> ✅ **먼저 할 일**: [03장 §7 현행 구성 진단](../03-cluster-setup/)을 실행해 현재 A인지 B인지 A+B인지를 명확히 확정하십시오. 이후 챕터의 절차가 갈립니다.

## 3. "hot을 통해서만 액세스"가 주는 성질

| 성질 | 결과 | 함의 |
|---|---|---|
| 단일 엔드포인트 | Spark 설정이 단순 (endpoint 1개) | 06장 설정이 간단해짐 |
| warm이 앱에 투명 | Iceberg 메타데이터의 경로가 항상 hot 기준 | 07장 경로 재작성이 중요 |
| warm 직접 접근 없음 | warm의 데이터 정합성을 앱이 검증하지 못함 | 09장 별도 점검 절차 필요 |
| hot이 SPOF | hot 장애 = 전체 중단 | 11장 F-01 |
| 전이 객체 읽기가 hot 자원 소모 | hot이 프록시 역할 → hot의 네트워크/CPU 부담 | 10장 §5 |

### ⚠️ warm 클러스터를 절대 직접 수정하지 말 것

방식 A(tier)에서 warm 버킷의 객체는 **AIStor 내부 포맷/이름 규칙**으로 저장됩니다.
사람이 warm에 직접 `mc cp`, `mc rm`, `mc mv` 를 하면 hot의 stub이 가리키는 대상이 사라져
**해당 객체는 영구 복구 불가**가 됩니다.

| 금지 행위 | 결과 |
|---|---|
| warm tier 버킷에 직접 쓰기/삭제 | hot stub ↔ 실데이터 불일치, 조회 시 오류 |
| warm tier 버킷에 별도 ILM 만료 규칙 적용 | 전이 데이터 소실 ⚠️ 치명 |
| warm tier 버킷 이름/리전 변경 | tier 설정 무효화 |
| 앱이 warm 엔드포인트로 직접 조회 | Iceberg 경로 불일치로 테이블 인식 실패 |

## 5. 네트워크 요건

| 출발 | 도착 | 포트/프로토콜 | 용도 | 필수 |
|---|---|---|---|---|
| Spark Pod | hot 엔드포인트 | 443/TCP (HTTPS) | 데이터 I/O | ✅ |
| Spark Pod | HMS | 9083/TCP (Thrift) | 카탈로그 | ✅ |
| Spark Pod | warm 엔드포인트 | - | **불필요** (열지 말 것) | ✖ |
| hot 노드 | warm 엔드포인트 | 443/TCP | transition, 전이 객체 읽기, 복제 | ✅ |
| warm 노드 | hot 엔드포인트 | 443/TCP | 양방향 복제 시에만 | 조건부 |
| 운영자 | hot/warm | 443/TCP | mc 관리 | ✅ |
| Prometheus | hot/warm | 9000 또는 별도 메트릭 포트 | 모니터링 | ✅ |
| HMS | 백엔드 DB | 5432/3306 | 메타 저장 | ✅ |

### 대역폭 산정 관점

| 트래픽 | 산정식 | 비고 |
|---|---|---|
| Transition | (일일 신규 데이터량) / (전이 소요 시간) | 스캐너 사이클 내에 몰림 → 버스트 |
| 복제 | (일일 신규 데이터량) × 1 / 86400 (평균) | 실제로는 쓰기 시점에 몰림 |
| 전이 객체 읽기 | (전이 데이터 대상 쿼리량) | 예측 어려움. 10장에서 실측 |
| 합계 피크 | 위 3개 동시 발생 가정 | hot↔warm 링크 사이징 근거 |

⚠️ transition과 복제가 같은 링크를 공유하면, 스캐너가 도는 동안 복제 backlog가 급증할 수 있습니다. 09장 모니터링에서 두 지표를 함께 봐야 하는 이유입니다.

## 6. 시간축으로 본 객체 생애주기 (방식 A 기준)

```
T+0h        Spark write → hot에 data/part-xxxx.parquet 생성 (v1, current)
            ├─ 복제 큐 등록 → 수초~수분 내 warm/warehouse 로 복제
            └─ ILM 평가 대상 (아직 1일 미경과 → 조치 없음)

T+24h       ILM 조건 충족 (age >= 1d)
            └─ 그러나 아직 아무 일도 일어나지 않음 ★
               ↓
T+24h ~ T+72h   Scanner가 해당 객체를 방문하는 시점에 비로소 transition 실행
            └─ 데이터가 warm-tier로 이동, hot에는 stub
               (이 구간이 "24~48시간 걸리는 것처럼 보이는" 정체)

T+48h~      warm tier 쪽 ILM 규칙(있다면)이 다시 age 평가
            ⚠️ warm-tier 버킷에 만료 규칙이 있으면 여기서 데이터 소실

이후        Spark 쿼리 → hot GET → hot이 warm에서 fetch → 응답
            (지연 증가, warm 의존)
```

★ 이 지점의 이해가 없으면 테스트 판정이 전부 어긋납니다. 상세: [02장 §5](../02-aistor-internals/)

## 7. 아키텍처 상 결정 사항 및 근거

| 결정 | 선택 | 근거 | 대안과 트레이드오프 |
|---|---|---|---|
| 카탈로그 | Hive Metastore | 기존 자산, 커밋 원자성 보장 | REST Catalog(운영 부담↓, 마이그레이션 필요), Hadoop Catalog(**S3에서 위험**) |
| 접근 경로 | hot 단일 | 앱 단순화, 경로 일관성 | 계층별 직접 접근(복잡·경로 깨짐) |
| FileIO | S3FileIO 권장 | S3 네이티브, 성능·기능 유리 | S3AFileSystem(하둡 생태계 호환) — 06장 §3 |
| Spark 실행 | K8s | 격리·탄력성 | YARN(기존 자원 재활용) |
| 전이 단위 | 프리픽스(`data/`) | 메타데이터 보호 | 태그 기반(관리 복잡), 버킷 분리(테이블 구조 변경 필요) |
| Versioning | ON | 복제 전제 조건 | OFF 시 복제 불가 |

## 8. 이 챕터 요약

1. 데이터 경로는 hot 단일 진입점이며, 전이가 시작되면 **warm이 쿼리 경로의 동기 의존성**이 된다.
2. hot→warm 방식은 A(tier)와 B(복제+만료)가 근본적으로 다르며, 현행이 무엇인지 먼저 확정해야 한다.
3. Iceberg 데이터에 **age 기반 expiration은 금지**, transition만 허용한다.
4. warm은 절대 직접 조작하지 않는다.
5. ILM 규칙 충족 시각 ≠ 실행 시각. 그 사이를 메우는 것이 Scanner다.
